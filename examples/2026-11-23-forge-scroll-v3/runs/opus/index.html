For engineering leads already running coding agents

Your agents can write the code. Forge runs the shop around them.

XYZ Forge is a local-first operations system for running Claude Code, Codex, agy and other agents as a workforce on your own repositories. It doesn't replace the agent. It handles the work around it: specified tasks, lanes that can't collide, gates that have to pass, and a receipted record of what landed.

capture→rate→plan→preflight→execute→gate→land→record

Each stage is a CLI verb or a skill, and each artifact is a file on your disk. The coordination layer needs no server, no account and no API key.

01 · Capture & rateIs this work written down?

Unattended agents fail for boring reasons. The first is a vague ticket.

GH-212 is one line in an issue tracker. That's enough for a human to start on. An agent working overnight needs more, so Forge starts by turning the issue into a file.

capture

Issue-first intake. The GitHub issue becomes a capture doc in PROJECT/1-INBOX/, plus a parked row in the release ledger. The capture doc records why the work matters, the phases, and a verification contract: how anyone, human or agent, can tell it's done.

/idea and /triage scaffold that doc and draft a first "why." They are front doors, not a spec generator. You and your LLM still write the spec. Forge just won't run work that doesn't have one.

rate

Scored backlog. Every item is rated on four axes, so "what runs next" has a reason you can read. GH-212 is customer-facing and cheap, so it moves up.

02 · Plan & preflightCan it run while I sleep?

Two lanes that touch the same file shouldn't run on the same night.

GH-212 isn't alone in the queue. The wave planner checks the exact write sets before anything is scheduled. Preflight then asks the question that matters before you leave: is this specified well enough to run unattended?

plan

Lanes are scheduled by the files they declare they will write. If two lanes overlap, they go in different waves. That one rule prevents most of the overnight merge mess.

preflight

Before a single turn starts, preflight runs freshness probes, checks whether the work has already landed, and confirms the verification gate can actually start. Its output is a readiness verdict.

Preflight · GH-212illustrative

  • Capture doc has why, phases, contract
  • Not already landed on development
  • Gate command starts in a clean worktree
  • Write set disjoint from wave-1 peers
READY — admitted to wave 1

No governance in a repo? Consult and Relay still work. Preflight downgrades its doc-shaped checks to advisory and still gives a verdict. Swarm and Marathon need PDDA installed.

03 · ExecuteWhat is the agent allowed to touch?

The agent drives through its own CLI. Forge sets the boundaries.

GH-212 runs as a relay. A producer agent builds, a reviewer agent critiques, and they hand off one headless turn at a time until the change converges. Each turn runs inside the same containment.

relay · GH-212 · illustrative transcript
turn 1  producer  codex · worktree /tmp/…/gh-212
        claim   src/exports/csv.ts  granted
        edit    src/exports/csv.ts
        edit    test/exports/csv.test.ts
        edit    src/server.ts     not allowlisted · dropped
        copy-back 2 files            ok

turn 2  reviewer  tighter allowlist
        finding  stream not closed on client abort
        verdict  changes requested

turn 3  producer
        edit    src/exports/csv.ts
        git commit                   blocked — repo reset
        copy-back 1 file             ok

turn 4  reviewer
        verdict  converged   → hand to gate
pushes this run: 0

Illustrative output, not a real log format. The behaviours (copy-back of allowlisted files only, commit reset, no pushes) are the documented ones.

  • Path-scoped claimsThe tick kernel serializes claims with an O_EXCL lock over an append-only event log, so two agents on overlapping paths take turns instead of racing.
  • Path allowlistEach turn has an allowlist. Reviewer turns get a tighter one.
  • Worktree isolationThe agent writes to a throwaway worktree. Only allowlisted files are copied back.
  • Commit-bypass guardIf an agent commits in the middle of a turn, the repo is reset.
  • Watchdog & typed exitsA wall-clock limit per turn, and exit codes that never report a timeout as a defect.
  • No pushes, everA turn shim never pushes. Landing is a separate step behind a gate.
Consult

04 · Gate, land, recordDid anything prove it works?

The reviewer said "converged." The gate decides.

An agent agreeing with another agent isn't evidence. GH-212 lands only after the verification contract from the capture doc runs and passes. Then it's written into a ledger you can merge, audit and resume from.

Deterministic: may block

Anything expressible as a regex, schema or file check is checked mechanically, and it can stop the line.

Advisory: may not block

LLM review can warn, rank or propose. It can never block on its own.

gate

A gate has to be able to start before turn 1. Preflight already checked that. When it runs, it is capped on CPU, wall clock and memory (RSS). A gate that goes over budget is killed and exits 108, which escalates separately, so a runaway test suite is never mistaken for a broken change.

If your target repo already has failing tests, --pre-advance-baseline <rc> lets the gate accept that known exit code while still stopping on new regressions.

land

Only a gated phase lands. If a run is interrupted, marathon-recover.sh gives you a read-only report. Any commit that landed without an approval event is flagged UNGATED COMMIT: treat it as unverified, then re-run the gate or revert.

record

The Product Release System ledger is SQLite plus a git-mergeable SQL dump, with receipted writes. It answers two questions: what did we promise, and what shipped with evidence?

Docs are runtime state. Work has to be stoppable, resumable and hand-offable from PROJECT/** alone. Drift between the docs and the code counts as a defect, so "done" means the suite is green and the doc contract holds.

05 · Before you adoptBe clear-eyed

Beta, single-operator, and honest about it.

Forge has been used hard by its author on real repositories. Several of its guards exist because an earlier version destroyed work. That counts in its favour, and it's also a warning.

Where it stands

Beta. One primary operator and a small set of collaborators. Most commits are written by agents. No published release tags yet.

Weakest areas: the frozen Bash fallback paths, and Python static analysis, which doesn't exist yet. The tick kernel has no stale-lock detection, so a hard kill mid-claim leaves a lock you remove by hand.

Flywheel (intake → execution → review → landing → next task) has landed real fixes. Two tasks advancing end to end without intervention is still unproven.

What it is not

  • Application lifecycle management: no multi-user identity, RBAC or SSO
  • Compliance tooling: no certification or regulatory traceability matrix
  • A spec generator: it expects specified work and doesn't write the spec
  • A model sandbox: agents choose commands through their own runtimes

Local-first is a deliberate constraint, not a missing feature. The operator is the only decision authority.

Sizing an unattended run

16 GB RAM supports the serial marathon route. Plan on 32 GB for per-lane parallel dispatch, after budgeting it yourself.

Measured on a 32 GB M1 Max: a serial marathon averaged 2.19 GB (2.26 GB peak) with a builder, a reviewer and three pytest gates running. Budget 1.5–2 GB per lane, plus your own test suite's memory.

Prove the kernel in 60 seconds. Then try a relay.

Needs Node 18+ and git. No accounts, no keys. Do it on a branch, and keep independent backups. Forge is provided as-is, and agent automation is inherently risky.

  1. Run the 14 kernel testsSub-second. Checks that the claim/lock/projection core works on your machine.
  2. Wire the pre-push gateOnce per clone. Git hooks don't travel with a clone, so a fresh clone has no gate until you install it.
  3. Run the full suite, outside the sandbox5–10 minutes in parallel mode. Under a sandboxed agent harness it prints nothing for minutes and then fails. That's the repo's most common false alarm.
  4. Start with Consult or RelayNeither needs governance. Add PDDA when you want Swarm or Marathon.
